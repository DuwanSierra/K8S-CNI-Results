\chapter{Abstract}
Kubernetes does not impose a network plugin: it leaves that choice to each team, which usually makes it without comparative metrics at hand. Choosing blindly is expensive twice over, in oversized infrastructure (CPU and memory) and in an incomplete security posture. This thesis builds the missing evidence, and builds it reproducibly, through infrastructure as code, automated benchmarks, and a multi-criteria decision analysis (MCDA) model.

Four plugins ---Flannel, Calico, Cilium, and Antrea--- were evaluated on a high-availability K3s cluster deployed on DigitalOcean. For each one the study measured TCP throughput, connection-establishment latency, retransmissions, and the CPU and memory consumed by the CNI agent, along with the effect of applying Zero Trust network policies. Those measurements feed an MCDA model tuned to the use profile (Fintech/security, Streaming/performance, and IoT/limited resources) and a web prototype that presents the recommendation.

No plugin proved superior across all criteria. Calico achieved the highest TCP throughput (1804.40 Mbps) and the lowest connection-establishment latency, while Flannel recorded the lowest retransmission rate and the smallest resource footprint. The study also found that Flannel, the CNI K3s ships by default, accepts NetworkPolicies through the Kubernetes API but never enforces them in its data plane, which amounts to a security false positive, and that Cilium was the only plugin able to enforce layer-7 (HTTP) policies. With no outright winner, the model recommends a different plugin for each profile: Cilium for Fintech, Calico for Streaming, and Flannel for IoT, the latter by a narrow margin.

\textbf{Keywords:} Kubernetes, CNI, NetworkPolicy, Zero Trust, MCDA, QoS, eBPF.
