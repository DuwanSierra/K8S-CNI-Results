\chapter{Resumen}
Kubernetes no impone un plugin de red: deja esa elección en manos de
cada equipo, que casi siempre la toma sin métricas comparativas a la
mano. Decidir a ciegas sale caro por partida doble, en infraestructura
sobredimensionada (CPU y memoria) y en una postura de seguridad
incompleta. Este trabajo construye la evidencia que falta y lo hace de
forma reproducible, con infraestructura como código, \emph{benchmarks}
automatizados y un modelo de decisión multicriterio (MCDA).

Se evaluaron cuatro plugins ---Flannel, Calico, Cilium y Antrea---
sobre un clúster K3s en alta disponibilidad desplegado en DigitalOcean.
De cada uno se midió el \emph{throughput} TCP, la latencia de
establecimiento, las retransmisiones y el consumo de CPU y memoria del
agente CNI, además del efecto de aplicar políticas de red Zero Trust.
Esas mediciones alimentan un modelo MCDA que se ajusta al perfil de uso
(Fintech/seguridad, Streaming/rendimiento e IoT/recursos limitados) y un
prototipo web que expone la recomendación.

Ningún plugin resultó superior en todos los criterios. Calico alcanzó
el mayor throughput TCP (1804.40 Mbps) y la menor latencia de
establecimiento, mientras que Flannel registró la menor tasa de
retransmisión y la huella de recursos más baja. También se comprobó que
Flannel, el CNI que K3s trae por defecto, acepta NetworkPolicies en la
API de Kubernetes pero no las aplica en su plano de datos, lo que
constituye un falso positivo de seguridad, y que Cilium fue el único
capaz de aplicar políticas de capa 7 (HTTP). Como no hay un ganador
absoluto, el modelo recomienda un plugin distinto según el perfil:
Cilium para Fintech, Calico para Streaming y Flannel para IoT, este
último por un margen estrecho.
